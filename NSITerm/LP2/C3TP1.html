    TP - Modularité et mise au point de programmes⚓︎

    Thématique : Conception et utilisation d'un module de gestion du temps⚓︎

    Durée: 2h

    Compétences du programme NSI mobilisées :

    • Spécifier une interface et la séparer de son implémentation.
    • Utiliser des API ou des bibliothèques, exploiter leur documentation.
    • Créer des modules simples et les documenter.
    • Documenter un programme et rédiger des préconditions à l'aide d'assertions assert.

    Pratiques complémentaires abordées dans ce TP (conventions Python utiles, mais non exigibles) :

    • Gérer l'espace de noms lors d'un import (import ... as ... plutôt que from ... import *).
    • Protéger le code de test d'un module avec la clause if __name__ == "__main__":.

    Contextualisation⚓︎

    Lors du développement d'un projet informatique complexe, réécrire les mêmes fonctions de calcul de durées ou de conversion de temps dans chaque fichier est inefficace et source d'erreurs.

    L'objectif de ce TP est de découvrir, puis d'étendre, un module réutilisable nommé horloge, qui fournit des services de conversion et de calcul sur les durées exprimées en secondes, minutes et heures.

    Un fichier zippé contenant le notebook jupyter ainsi que les modules (compilés) sera fourni.

    Avant de commencer: trois mots à ne pas confondre⚓︎

    Ce TP emploie constamment trois mots — interface, implémentation, API — . Il faut prendre le temps de les distinguer maintenant, car l'intégralité du TP y fait référence.

    • Interface : ce que l'on voit et utilise de l'extérieur d'une fonction, d'un module ou d'une structure de données — son nom, ses paramètres, ce qu'elle fait (en langage naturel, dans sa docstring), et ses préconditions. C'est un contrat entre celui qui écrit le code et celui qui l'utilise: tant que le contrat est respecté, peu importe comment il est tenu!
    • Implémentation : le code qui réalise réellement ce que l'interface promet — les lignes à l'intérieur du corps de la fonction. Deux implémentations différentes peuvent respecter exactement la même interface (produire le même résultat par un chemin interne différent) sans que l'utilisateur du module ne s'en aperçoive ni n'ait besoin de le savoir.
    • API (Application Programming Interface ou interface de programmation) : ce terme désigne l'ensemble des interfaces (fonctions, classes, constantes...) qu'un module ou une bibliothèque met à disposition.

    Une API et une interface, c'est la même idée ; on parle d'API quand on désigne l'ensemble des services offerts par tout un module, plutôt qu'une seule fonction isolée. Le mot est aussi très employé pour désigner des services web — l'API du réseau X, par exemple — mais c'est exactement le même principe : une façade documentée, derrière laquelle l'implémentation reste cachée et peut changer.

    Analogie. Un four à micro-ondes a une interface : les boutons puissance, durée, marche. Vous n'avez pas besoin de savoir comment fonctionne le magnétron à l'intérieur (l'implémentation) pour faire chauffer votre plat : connaître l'interface suffit. Un fabricant peut changer entièrement l'électronique interne d'un nouveau modèle (nouvelle implémentation) sans toucher aux boutons (même interface) : vous continueriez à vous en servir exactement de la même façon.

    Dans ce TP :

    • en partie 1, le rôle d'utilisateur est privilégié: on ne voit que l'API de horloge (le tableau ci-dessous), jamais son implémentation ;
    • en partie 2, c'est le rôle de développeur qui est visé: on implémente une extension (le corps des fonctions), en respectant une interface;
    • la partie 3 est réservée au test de la robustesse du module.

    Auto-vérification — sans remonter au texte ci-dessus, associez chaque définition au bon mot (interface, implémentation, API) :

    1. Ensemble des fonctions et de leur documentation qu'un module met à disposition, sans exposer le code interne. → ..............?
    2. Le code réel, à l'intérieur du corps des fonctions, qui réalise le travail. → ............?
    3. Terme le plus souvent utilisé pour désigner l'interface de tout un module ou d'une bibliothèque, plutôt que d'une seule fonction isolée. → ...............?

    def en_secondes(nombre_de_jours):

print("Avant l'import :")

print("Après 'from horloge import *")
print("en_secondes(2) =", end=" ")
try:
    print(en_secondes(2))
except Exception as e:
    print("erreur :", e)

    La fonction locale en_secondes définie dans cette cellule a été remplacée par celle du module horloge. L'erreur obtenue (en_secondes() takes exactly 3 positional arguments (1 given)) provient de la signature en_secondes(h, m, s) du module, pas de la fonction locale à un seul paramètre.

    On remarque qu'aucun message n'a prévenu ce remplacement au moment de l'import. C'est exactement le risque de from ... import *, qui importe tous les noms du module dans l'espace de noms courant et qui peut donc écraser silencieusement des noms déjà utilisés.

    Avec import horloge as hor, ce risque disparaît: on accède toujours à la fonction du module via hor.en_secondes, qui ne peut jamais entrer en conflit avec une fonction locale nommée en_secondes.

    Répondre maintenant aux deux questions ci-dessus, en s'appuyant sur cette observation.

    Partie 2 : Extension et mise au point d'un module⚓︎

    Il s'agit désormais de se placer dans le rôle de concepteur / développeur.

    On n'a pas accès au code source de horloge, on ne dispose que de son API, comme en partie 1. On ne peut donc pas modifier horloge. Il s'agit d'écrire un nouveau module horloge_ext.py, qui sera une extension de horloge. Les fonctions du nouveau module appelleront les fonctions de horloge sans avoir besoin de savoir comment elles sont écrites. C'est exactement l'intérêt d'une interface.

    Description du module horloge_ext.py⚓︎

    Le nouveau module horloge_ext.py commence par import horloge as hor et fournit deux nouvelles fonctionnalités :

    1. difference_durees(t1: tuple[int, int, int], t2: tuple[int, int, int]) -> int :

      • prend deux tuples au format (h, m, s) représentant deux instants;
      • renvoie l'écart absolu en secondes entre ces deux instants (toujours positif ou nul);
      • utilise la fonction en_secondes du module horloge (c'est-à-dire hor.en_secondes).

    2. additionner_durees(duree1_sec: int, duree2_sec: int) -> tuple[int, int, int] :

      • calcule la somme de deux durées exprimées en secondes et renvoie le résultat sous forme de tuple (h, m, s) en réutilisant hor.en_hms.

    Exigences de qualité et de mise au point - Interface à compléter⚓︎

    • Documentation: chaque fonction doit contenir une docstring décrivant le rôle, chaque paramètre et la valeur de retour, sur le modèle des docstrings de en_secondes, en_hms et formater_duree qu'on peut consulter avec help(hor.en_secondes) (rôle, puis une ligne par paramètre, puis "renvoie ...").
    • Assertions (assert) : chaque fonction doit valider la conformité de ses arguments d'entrée (type et domaines de valeurs). Les fonctions de horloge contrôlent déjà leurs propres arguments, il s'agira de vérifier cette conformité pour les deux fonctions à écrire.
    • Clause if __name__ == '__main__': ajouter des tests unitaires validant les nouvelles fonctions lors de l'exécution directe du fichier.
    • Table d'interface : comme pour l'API d'origine (tableau de la partie 1), compléter la table Markdown ci-dessous en spécifiant l'interface des deux nouvelles fonctions, avant de les implémenter.

    ⚠️ À lire avant de continuer : Python ne recharge pas un module modifié, tout seul!⚓︎

    Le nouveau module horloge_ext.py a été écrit sur le disque. Dès qu'on l'importe une première fois, Python en garde une copie en mémoire. Si on corrige ensuite le code et ré-exécute la cellule, un nouvel import horloge_ext ne relira pas le fichier: Python considère que le module est déjà chargé et réutilise la version qu'il a en cache.

    C'est un point essentiel de la notion de module en Python, pas un simple détail technique: chaque fois qu'on modifie horloge_ext.py, il faut exécuter la cellule suivante pour recharger explicitement le module avec importlib.reload, afin que la suite du TP utilise bien la dernière version. (Le module horloge, lui, ne change pas : il n'y a aucune raison de le recharger.)

print("Module horloge rechargé : additionner_durees disponible ?",
      hasattr(horloge_ext, "additionner_durees"))
