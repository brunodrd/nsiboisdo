    📖 Cours 1 : Le modèle relationnel⚓︎

    Programme

    Contenus Capacités attendues Commentaires
    Modèle relationnel : relation, attribut, domaine, clef primaire, clef étrangère, schéma relationnel. Identifier les concepts définissant le modèle relationnel. Ces concepts permettent d'exprimer les contraintes d'intégrité (domaine, relation et référence).

    À la fin de ce chapitre, je sais…

    1. Définir une base de données et dire ce qu'apporte le modèle relationnel.
    2. Nommer les éléments d'une relation : attribut, domaine, n-uplet, valeur.
    3. Écrire le schéma d'une relation avec ses domaines.
    4. Justifier qu'un attribut, ou un ensemble d'attributs, peut ou ne peut pas servir de clé primaire.
    5. Repérer une clé étrangère et dire à quelle clé primaire elle fait référence.
    6. Énoncer les trois contraintes d'intégrité et dire laquelle explique le refus d'une modification.

    0. 🔎 Activité d'amorce : explorer une base⚓︎

    L'activité C8A1 a montré les défauts d'un fichier unique : informations répétées, incohérences, mises à jour risquées. La solution trouvée consistait à répartir les données dans plusieurs tables reliées entre elles. Ce cours donne le vocabulaire exact de cette organisation.

    À faire

    Ouvrir la base Livres_2 dans l'interface phpMyAdmin.

    1. Combien de tables cette base contient-elle ? Relever leurs noms.
    2. Relever le nom et le type de chaque colonne de la table auteur.
    3. Combien de lignes la table usager contient-elle ?
    4. Dans quelle table trouve-t-on la date de retour d'un livre emprunté ? Y trouve-t-on aussi le titre du livre ?

    1. 📚 Base de données et modèle relationnel⚓︎

    Définition : base de données

    Une base de données est un ensemble de données structurées, enregistrées sur un support persistant. « Persistant » signifie que les données existent encore après l'arrêt du programme ou de la machine.

    Un modèle de données fixe la façon de structurer ces données. Le modèle relationnel est le plus répandu. Son idée centrale : toutes les données sont rangées dans des tableaux à deux dimensions, appelés relations, et rien d'autre.

    Construire une base demande trois étapes :

    • repérer les objets à décrire et ce qui les relie : cette étape de conception n'est pas au programme de terminale ;
    • représenter ces objets par des relations ;
    • énoncer les contraintes que les données doivent toujours respecter.

    Le logiciel qui gère une base de données s'appelle un système de gestion de bases de données (cours C8C4). Dans ce chapitre, c'est MySQL, utilisé à travers l'interface phpMyAdmin.

    Culture : l'origine du modèle relationnel

    Le modèle relationnel a été proposé en 1970 par Edgar F. Codd, informaticien britannique qui travaillait chez IBM aux États-Unis. Le mot « relation » vient des mathématiques, où il désigne un ensemble de n-uplets.

    2. 🧱 Relation, attribut, domaine⚓︎

    Définition : relation, attribut, domaine, n-uplet

    • Une relation porte un nom et contient un ensemble de n-uplets. On la représente par une table : chaque n-uplet est une ligne.
    • Un attribut est le nom d'une colonne. Tous les attributs d'une relation ont des noms différents.
    • Le domaine d'un attribut est l'ensemble des valeurs qu'il peut prendre. Il joue le rôle du type en programmation.
    • Un n-uplet donne une valeur à chaque attribut, prise dans le domaine de cet attribut.

    Sur ce schéma, la relation livre a quatre attributs. Le n-uplet encadré donne la valeur Flammarion à l'attribut editeur et la valeur 2015 à l'attribut annee, dont le domaine est celui des entiers.

    Dans ce cours, les domaines sont notés comme dans les sujets d'examen :

    Domaine Valeurs Exemple dans Livres_2
    INT nombres entiers annee, cp, code_barre, a_id
    TEXT chaînes de caractères titre, nom, isbn
    DATE dates retour

    Une relation est un ensemble de n-uplets. Ce mot a deux conséquences :

    • les n-uplets n'ont pas d'ordre : la table peut être affichée dans n'importe quel ordre de lignes, c'est la même relation ;
    • une relation ne contient jamais deux n-uplets identiques.

    Le vocabulaire du modèle relationnel et celui de l'usage courant désignent les mêmes objets.

    Modèle relationnel Usage courant, langage SQL
    relation table
    n-uplet ligne, enregistrement
    attribut colonne
    domaine type

    3. 📐 Schéma d'une relation⚓︎

    Définition : schéma d'une relation

    Le schéma d'une relation est son nom, suivi de la liste de ses attributs, chacun avec son domaine.

    Le schéma de la relation livre s'écrit :

    livre (titre : TEXT, editeur : TEXT, annee : INT, isbn : TEXT)

    Quand les domaines sont évidents ou donnés ailleurs, on écrit le schéma sans eux : livre (titre, editeur, annee, isbn). Le soulignement de isbn est expliqué à la section 4.

    Le schéma décrit la structure de la relation. Les n-uplets forment son contenu. Ajouter un livre change le contenu, pas le schéma. Cette distinction est reprise au cours C8C2.

    À faire

    1. Écrire le schéma de la relation auteur, avec les domaines.
    2. Écrire le schéma de la relation usager, avec les domaines.
    3. Un élève propose TEXT comme domaine de l'attribut cp. Citer un avantage et un inconvénient de ce choix.

    4. 🔑 Clé primaire⚓︎

    Pour retrouver un n-uplet sans ambiguïté, il faut un moyen de le désigner. C'est le rôle de la clé primaire.

    Définition : clé primaire

    La clé primaire d'une relation est un attribut, ou un ensemble d'attributs, choisi pour identifier chaque n-uplet : deux n-uplets différents n'ont jamais la même valeur de clé primaire, et cette valeur est toujours renseignée. Dans un schéma, la clé primaire est soulignée.

    Dans la relation livre, la clé primaire est isbn : l'ISBN est un numéro attribué à chaque édition d'un livre, deux éditions différentes n'ont jamais le même.

    À ne pas confondre

    Une clé primaire se justifie par le sens des données, pas par l'extrait que l'on a sous les yeux. Dans la base Livres_2, aucun titre n'apparaît deux fois. Pourtant titre ne peut pas servir de clé primaire : deux éditions d'un même roman portent le même titre, et la base doit pouvoir les accueillir toutes les deux. La bonne question n'est pas « les valeurs sont-elles toutes différentes aujourd'hui ? » mais « pourraient-elles un jour être égales ? ».

    Trois situations se rencontrent.

    • Un attribut naturel convient. C'est le cas de isbn pour livre.
    • Aucun attribut naturel ne convient. Dans usager, deux personnes peuvent porter le même nom : la base contient déjà deux usagers nommés PAYET. On ajoute alors un attribut créé pour cela, ici code_barre. De même, a_id identifie chaque auteur.
    • Il faut plusieurs attributs. Dans auteur_de, un auteur a écrit plusieurs livres et un livre peut avoir plusieurs auteurs : ni a_id seul ni isbn seul n'identifie une ligne. La clé primaire est le couple (a_id, isbn). On parle de clé primaire composée.

    Les schémas des cinq relations de la base, clés primaires soulignées :

    • livre (titre, editeur, annee, isbn)
    • auteur (a_id, nom, prenom)
    • auteur_de (a_id, isbn)
    • usager (nom, prenom, adresse, cp, ville, email, code_barre)
    • emprunt (code_barre, isbn, retour)

    Méthode : justifier qu'un attribut ne peut pas être clé primaire

    Il suffit de décrire une situation réaliste où deux n-uplets différents auraient la même valeur pour cet attribut. Exemple : « nom ne peut pas être la clé primaire de usager, car deux usagers peuvent porter le même nom de famille ».

    À faire

    1. L'attribut annee peut-il servir de clé primaire à la relation livre ? Justifier.
    2. Le couple (titre, editeur) peut-il servir de clé primaire à la relation livre ? Justifier.
    3. La clé primaire de emprunt est isbn. Qu'est-ce que ce choix interdit ? Est-ce raisonnable pour une bibliothèque qui possède un seul exemplaire de chaque livre ?

    5. 🔗 Clé étrangère⚓︎

    La relation emprunt ne contient ni le titre du livre emprunté ni le nom de l'emprunteur. Elle contient seulement un ISBN et un code-barres. Ces deux valeurs suffisent : elles désignent un n-uplet de livre et un n-uplet de usager. On évite ainsi de recopier les mêmes informations à plusieurs endroits, ce qui était le défaut du fichier unique de l'activité C8A1.

    Définition : clé étrangère

    Une clé étrangère est un attribut, ou un ensemble d'attributs, d'une relation, dont chaque valeur doit être une valeur de la clé primaire d'une relation. On dit que la clé étrangère fait référence à cette clé primaire. Dans un schéma, une clé étrangère est précédée du signe #.

    Sur ce schéma, les deux ISBN présents dans emprunt existent dans livre. L'ISBN de Lolita n'apparaît pas dans emprunt : ce livre n'est pas emprunté, et rien ne l'oblige à l'être. La contrainte ne joue que dans un sens.

    Le schéma complet de la base, avec clés primaires et clés étrangères :

    • livre (titre, editeur, annee, isbn)
    • auteur (a_id, nom, prenom)
    • auteur_de (#a_id, #isbn)
    • usager (nom, prenom, adresse, cp, ville, email, code_barre)
    • emprunt (#code_barre, #isbn, retour)

    Un attribut peut appartenir à la fois à la clé primaire et à une clé étrangère : c'est le cas de isbn dans emprunt, et des deux attributs de auteur_de. Cette dernière relation ne contient que des clés étrangères. Elle sert uniquement à relier les auteurs et les livres. Elle répond au problème du livre écrit par plusieurs auteurs, resté sans solution dans l'activité C8A1.

    Attention : le nom de l'attribut ne fait pas la clé étrangère

    Dans Livres_2, une clé étrangère porte le même nom que la clé primaire qu'elle référence. Ce n'est pas une règle : dans un sujet, un attribut id_realisateur peut faire référence à la clé primaire id_artiste d'une autre relation. C'est l'énoncé, ou le signe #, qui indique les clés étrangères.

    Pour aller plus loin : une clé étrangère vers sa propre relation

    Une clé étrangère peut faire référence à la clé primaire de la relation où elle se trouve. Exemple : dans une relation employe (id, nom, #id_responsable), l'attribut id_responsable contient l'identifiant d'un autre employé.

    À faire

    1. À quelle clé primaire l'attribut code_barre de emprunt fait-il référence ?
    2. L'usager dont le code-barres est 421921003090881 a trois emprunts en cours. Est-ce compatible avec la définition d'une clé étrangère ? Est-ce compatible avec la clé primaire de emprunt ?
    3. Le livre « The Practice of Programming » a deux auteurs. Combien de n-uplets de auteur_de portent son ISBN ?

    6. 🛡️ Contraintes d'intégrité⚓︎

    Définition : contrainte d'intégrité

    Une contrainte d'intégrité est une règle que les données de la base doivent respecter à tout instant. Le système de gestion de bases de données refuse toute modification qui la violerait.

    Le modèle relationnel définit trois contraintes. Chacune découle d'un concept vu plus haut.

    Contrainte Ce qu'elle impose Concept
    de domaine chaque valeur appartient au domaine de son attribut domaine
    de relation chaque n-uplet a une valeur de clé primaire, différente de toutes les autres clé primaire
    de référence chaque valeur d'une clé étrangère existe dans la clé primaire référencée clé étrangère

    Exemple : trois modifications refusées dans Livres_2

    • Domaine. Ajouter un livre dont l'année est le texte deux mille douze : l'attribut annee a pour domaine INT.
    • Relation. Ajouter un usager dont le code-barres est 934701281931116 : cette valeur de clé primaire est déjà celle d'un autre usager.
    • Référence. Ajouter un emprunt pour un ISBN qui n'existe pas dans livre. Ou encore supprimer de livre un livre emprunté : la ligne de emprunt qui porte son ISBN ne désignerait plus rien.

    La contrainte de référence agit donc dans deux situations : quand on ajoute une valeur de clé étrangère, et quand on supprime ou modifie une valeur de clé primaire référencée. Les requêtes correspondantes sont étudiées au cours C8C3, section 6.

    Attention : cohérent ne veut pas dire vrai

    Les contraintes d'intégrité garantissent que les données sont cohérentes entre elles. Elles ne garantissent pas qu'elles sont exactes. Rien n'empêche d'enregistrer qu'Isaac Asimov est l'auteur de Lolita : l'auteur existe, le livre existe, les trois contraintes sont respectées.

    7. 🧠 Synthèse⚓︎

    À retenir

    • Une base de données relationnelle est un ensemble de relations.
    • Une relation a un nom, des attributs et un ensemble de n-uplets, sans ordre ni doublon. Chaque attribut a un domaine.
    • Le schéma d'une relation donne son nom et ses attributs avec leurs domaines : c'est la structure, les n-uplets sont le contenu.
    • La clé primaire, soulignée, identifie chaque n-uplet. Elle peut être composée de plusieurs attributs. Elle se justifie par le sens des données.
    • Une clé étrangère, précédée de #, fait référence à une clé primaire : chacune de ses valeurs doit y exister.
    • Trois contraintes d'intégrité : de domaine, de relation, de référence. Une modification qui en viole une est refusée.

    8. 📝 Pour s'entraîner⚓︎

    Ces questions se traitent sur papier, avec le schéma complet de la base Livres_2 sous les yeux (section 5). Chaque réponse est justifiée par une phrase complète. L'exercice marqué ⭐ est un prolongement.

    1. Citer les attributs de la relation emprunt et le domaine de chacun.
    2. Dans la base, tous les usagers ont actuellement des couples (nom, prenom) différents. Expliquer pourquoi ce couple ne peut tout de même pas servir de clé primaire à usager.
    3. Expliquer pourquoi l'attribut code_barre ne peut pas servir de clé primaire à la relation emprunt.
    4. Expliquer pourquoi l'attribut a_id seul ne peut pas servir de clé primaire à la relation auteur_de.

    5. La base contient l'auteur d'identifiant 30 (George Orwell) et l'usager de code-barres 421921003090881. Le livre d'ISBN 978-0141391601 (Lolita) n'est pas emprunté. Celui d'ISBN 978-2081358881 (Mrs Dalloway) l'est. Aucun auteur n'a l'identifiant 200 et aucun usager n'a le code-barres 111111111111111. Pour chaque n-uplet, dire s'il peut être ajouté à la relation indiquée. S'il est refusé, nommer la contrainte violée.

      Relation N-uplet
      a auteur (30, 'Verne', 'Jules')
      b auteur (200, 'Verne', 'Jules')
      c emprunt (421921003090881, '978-0141391601', '2020-05-12')
      d emprunt (421921003090881, '978-2081358881', '2020-05-12')
      e emprunt (111111111111111, '978-0141391601', '2020-05-12')
      f livre ('Dune', 'Pocket', 'deux mille douze', '978-2266320481')

    6. Peut-on supprimer de la relation usager l'usager de code-barres 421921003090881 ? Justifier.

    ⭐ Exercice de prolongement – Garder l'historique des emprunts⚓︎

    La bibliothèque souhaite conserver la trace de tous les emprunts passés, et non plus seulement des emprunts en cours.

    1. Expliquer pourquoi le schéma actuel de emprunt ne le permet pas.
    2. Proposer un nouveau schéma pour emprunt, en ajoutant un attribut et en changeant la clé primaire.
    3. Avec ce nouveau schéma, comment reconnaître un emprunt en cours ?
